## 結論と作業範囲

当てずっぽうの実装変更を再開するのではなく、既存の割り当て標本・Tier 1生成コード・契約と、入力の構造を照合した。次に試す根拠のある候補を特定できた。本体・JSONサンプル・テストは変更しておらず、新しい通常計時も行っていない。以下は改善の保証や採用決定ではない。

## 1. 再帰getter内の変換パーサー生成を定義時へ移す

対象は `JsonParser/JSON.cs` のJValue。配列・オブジェクトの候補を試すたび、getterが新しいParserConverterを返す。

```csharp
// 現行の配列側。オブジェクト側も同形。
new RecursiveParser<IJSONValue>(
    () => new ParserConverter<JSONArray, IJSONValue>(
        JArray ?? throw new InvalidOperationException(),
        array => array))
```

提案は、再帰参照だけをgetterへ残し、変換の組み合わせを定義時に一度作ること。

```csharp
// 未実装の提案。既存の型だけで構成できる。
new ParserConverter<JSONArray, IJSONValue>(
    new RecursiveParser<JSONArray>(
        () => JArray ?? throw new InvalidOperationException()),
    array => array)
```

割り当て標本には、配列用Converterが955件、オブジェクト用が874件あり、スタックもこのgetterに対応している。新しいConverterの生成が実行時にも残っている証拠である。

根はJObjectを直接呼ぶ。残る100,000値はJValueを通り、まず配列候補を試す。そのうち配列16,454値以外の83,546値ではオブジェクト候補も試す。したがって文法と入力から、成功した木を作る経路だけでも計183,546回のConverter生成が必要になる。空配列の終了確認などの失敗試行はこの下限に含めていない。これは動的呼び出しカウンターの実測値ではなく、現行制御フローからの下限である。

変更後の目標は、この2種類の変換パーサーを定義時の各1個だけにすること。再帰のgetter呼び出し自体は残す。`RecursiveParser`一般にキャッシュを入れる案ではない。既存テストではgetterの毎回評価と、その都度返す異なるパーサーの利用を要求している。

静的初期化時にJArray/JObjectへアクセスせず、実際に解析するときに参照する順序も保つ。値の変換は成功時だけ行い、失敗カーソル・例外伝播を保つ。JSONの公開APIや文法を変える必要はない。ライブラリの構造を壊さず、サンプルの組み合わせの位置だけを直せるため、最初の候補として推奨する。

検証では、この2種類の実行中割り当てが消えることを先に確認する。その後、通常計時で全体の改善を判定する。閉じたジェネリック型と呼び出し位置が変わるので、割り当てが減ってもPGO等を含めた速度改善は未確認である。

## 2. 反復結果から文字列への二重配列化を省く

`JSON.cs`のDigitsとJStringは `new string([.. chars])` 相当で文字列を作る。OneOrMore/ZeroOrMoreは既に `ParsedValueBuffer.ToArray()` で所有権の独立したchar配列を確定しているため、文字列化の直前の配列化は2個目になる。

これはソースだけの推測ではない。JStringの変換が展開されたTier 1コードに `Enumerable.ToArray<char>` の呼び出し（51933行）と、その結果から文字列を作る呼び出し（51948行）が残っている。

提案は、確定結果が配列なら直接stringへコピーし、その他のIEnumerableには従来の具体化を残すこと。

```csharp
// 未実装の変換式の例。複数箇所へ重複展開する方針ではない。
chars => new string(chars is char[] array ? array : [.. chars])
```

反復処理の独立した結果配列も、最後のstringの確保・コピーも残る。借りたpool配列を結果へ流出させず、公開戻り値を配列型に変えず、入力位置から元の文字を再構成しない。失敗したWordParserの入力スライス案とは異なる変換境界である。

入力にはJStringで成功する文字列値とプロパティ名が計66,703個、うち非空は65,937個、計716,420文字ある。成功経路のこの文字量について、2個目のchar配列へのコピーが削減対象になる。空配列の共有や数値の別経路があるため、全char配列3,204標本を削減可能と扱わない。数字列の呼び出し数も、生数値トークン数だけから断定しない。

標準APIだけで表す候補として `string.Concat(IEnumerable<char>)` も確認した。.NET 10.0.12では、char列を列挙してValueStringBuilderへ追加する経路で、char配列をそのままstringへ一括コピーする特例ではない。既存の確定配列に対しては、直接string化の方が省ける処理を明確にできる。Concatの方が速い／遅いとは未測定で断定しない。[.NET 10.0.12の実装](https://github.com/dotnet/runtime/blob/v10.0.12/src/libraries/System.Private.CoreLib/src/System/String.Manipulation.cs)

配列表現への知識がサンプルへ入る点は保守上の負担になる。適用するなら変換境界へ局所化し、fallbackと理由を残す。空文字・長い文字列・エスケープ・非ASCII・数字列について結果を確認し、割り当て減少と通常計時を別々に評価する。

## 3. Sequence3の平坦化直前の中間結果を除く

本体の `SequenceParser3.cs` は次の構造で3要素を組み合わせる。

```text
Converter(Sequence2(p1, Sequence2(p2, p3)), nested => flat)
```

`char, 参照型, char` のTier 1では、外側Sequence2の非インライン呼び出し（38951–38954行）、nested結果の書き出し（39169–39185行）、24 byteのtupleコピー（38962–38965行）、flat結果への再包装（38980–38992行）が残っている。nested結果の参照書き込みにはhelperが2回ある。

一方、平坦化delegateの一致枝は既にインライン化されている（38968–38978行）。削減対象は「delegate呼び出し1回」ではない。nested ParseResultのレイアウトは48 byteだが、48 byte全体の一括コピーやヒープ確保を意味しない。Sequence3自身の委譲も独立した結果コピーとして数えない。

この型の経路は文字列／キー、配列、オブジェクトで使われる。入力構造から対応する成功機会は66,703＋16,454＋16,636＝99,793個。文字数に比例する削減ではない。試行を含む呼び出し数は別途計測が必要。

提案は「二つの子を順に解析し、成功時に最終projectionを直接適用する」内部共通経路を検討し、outer Sequence2とConverterの間だけに存在するnested結果を作らないこと。suffix Sequence2と最終結果は残す。arity 3～10ごとに子呼び出しを手書き展開する方針ではなく、具体的な内部抽象の形もまだ決定していない。

成功1回あたり、outer Sequence2への非インライン呼び出し1回、nested側の参照書き込みhelper 2回、24 byteのtupleコピーを除けるかが最初の検証目標になる。新しい実装が別のdispatchやコピーを生むなら、この目標は達成できない。ヒープ割り当て減少は主張しない。

### 適用範囲を狭くする根拠

JPairの `参照型, char, 参照型` では、既に両段のSequence2がインライン化され、中間状態がレジスター等で渡される枝がある（47009行以降、47344–47358行）。こちらに同じnested結果の一往復があるとはいえない。arity 4～10のコードも今回の採取にはない。ソース上の組み合わせ数を、そのまま機械語の呼び出し・コピー数に置き換えない。

共通化で、子の評価順序・回数、先行失敗時の短絡、例外、外部派生overrideを維持する必要がある。Sequence失敗時は開始カーソルへ戻す一方、一般のConverterは子が返した失敗カーソルを引き継ぐ。この違いを潰さない。公開APIや派生可能性を変えず、任意のConverter一般へ自動融合を広げない。既存PGO対策の内部呼び出しを共通の `Parse` へ戻す案でもない。

まず狭い候補でnested結果の返却境界・コピー・helperが本当に消えるか、既に良好なJPair側を壊さないかを確認する。消えなければこの削減仮説はそこで棄却する。消えた場合だけ、通常計時の候補とする。

## 補助候補と今回選ばない案

* JSONArrayは確定済みの要素配列を受け取るが、空Listへ一要素ずつAddする。AddWithResize由来の配列が少なくとも341標本ある。既知の要素数で最終Listを作れば、成長用配列とコピーを省ける。Collection式／コレクションコンストラクターの利用を検討できるが、公開される `Elements.Capacity` が変わり得るため、その影響は隠さない。JSONObjectの同様のコンストラクターは主文法で使われず、そこを変えても今回の速度改善根拠にならない。
* JSON空白は4個のCharParserのOr。既存ConditionalCharParserで `' ' or '\t' or '\r' or '\n'` を判定すれば、非空白の棄却時に4候補を試す必要がなくなる。文法上の評価回数削減は説明できるが、今回の標本ではその部分の費用を分離できていないため優先度は低い。`char.IsWhiteSpace`へ替えると受理する言語が広がるので不可。
* RecursiveParserのgetterのキャッシュ、任意の空白パーサーの省略、借用配列の外部返却、失敗カーソルの一律化は契約に反するため選ばない。
* 直前に撤回したnullガード削減・Word結果生成や、Or専用化・scratch容量変更は、新しい原因根拠なしに再試行しない。

## 実装へ進む場合の検証手順

### 継続調査で分かった設計上の負担

Sequence3案を具体化すると、通常のSequence2全体へprojectionの呼び出し経路を導入する必要がある。Func方式では新しいdelegate呼び出しが全Sequence2へ入り、非delegate方式でもstatic abstractなprojectionと内部型が必要になる。3要素だけに局所化した小変更ではなく、4〜10要素にも間接的に波及する。処理を手書き複製する案は採らず、現時点では設計負担を明示した保留候補とする。

既存の `要素を3つ持つSeqenceParserのテスト.cs` の「三つ目の解析に失敗」は、入力が `public statiac innt` で2個目も失敗するため、3個目まで到達する検証としては不十分。今回は変更していない。Sequence案へ進む場合は、この点と、消費後の失敗・後続呼び出しの抑止・派生overrideの検証を先に整理する必要がある。

補助候補の空白判定は、既存Tier 1のWithWhiteSpace内でもOr/Charの候補走査・型ガード・Current取得と範囲判定・IgnoreCase分岐が残る（同じjit.asmの38377〜38410行付近、Word内にも39933行付近から同形）。4回のvirtual呼び出しが残るという意味ではなく、ガード付きinline化後にも繰り返される判定が対象である。固定4文字のConditionalCharParserへ置換すれば、非空白の4候補走査を1回の文字取得へ減らせる。SPACEでは既存も最初の候補で成功するため、一律な速度改善は保証しない。Digitで使用する別predicateとのprofile混在も測定で確認する必要がある。

第1案の[再帰定義](2026-10-19-recursive-definition.md)と第2案の[二重配列化](2026-10-19-char-materialization.md)は、その後個別に実装・測定した。いずれも削減対象と割り当て減少は確認できたが、速度改善の採用条件を満たさず撤回した。以下は実行前に定めた判定手順であり、結果に合わせて変更していない。

実装へ進む場合は一候補ずつ扱い、複数案を一度に混ぜない。

1. 差分と契約を確認し、既存テストで不足する境界だけを補う。サンプル変更の場合は本体の高速化と分けて記録する。
2. 本体だけでなくJSONサンプルを含むソース・DLLを版ごとに固定する。サンプルを変えたのに本体DLLだけ差し替えて比較することはしない。全文消費・100,001ノード・結果木一致を両版で確認する。
3. 原因に対応する診断で、生成オブジェクト、2個目の配列、nested結果のコピーが実際に消えたか確認する。診断時間を速度評価へ混ぜない。
4. PGO有効・同一入力・MemoryStream込みの既存条件で、固定8組の新規プロセスをAB/BA交互に通常計時する。起動平均を比較単位とし、8個の対応log時間比の95% t区間で判定する。探索で上限が1未満なら、独立8組で同じ条件を確認する。都合のよい外れ値除外・組数延長・探索と確認の合算はしない。
5. 削減対象が消えても通常計時が改善しなければ、速度改善として採用しない。同じ根拠のまま微修正を際限なく試さず、新しい証拠が必要な状態として止める。

通常計時・機械的集計はLuna medium、仮説と採否は主担当。測定は直列実行し、PGO OFFで安定化させない。
