# JSON通常文字判定の重複削減 2026-10-19

JSONサンプルの通常文字を、引用符・バックスラッシュの2個のCharParserを否定する構成から、既存ConditionalCharParserの固定条件へ変更した。PGO有効・MemoryStreamからの読み込みを含む既存JSON入力で、探索8組に続く独立確認8組でも約5.3%短縮した。事前の性能採用基準を満たし、2026-10-19にユーザーが差分を確認して採用・コミットを指示した。実装と本記録を同じコミットへ保存する。

基準は、[空白判定の改善](2026-10-19-whitespace-predicate.md)を保存した `00a7efa938a41e182974db822f2b2ab2dba17ff8`。ライブラリ本体の一般的な高速化ではなく、既存コンビネーターを使うJSONサンプルの構成改善である。

## 実装と契約

変更前:

```csharp
static Parser<char> JChar =
    new OrParser<char>(
        new ExpectCharParser(
            new OrParser<char>(
                DoubleQuote,
                BackSlash)),
        ControlChar);
```

変更後:

```csharp
// 固定2文字の除外をまとめ、通常文字ごとの候補走査と文字の再取得を省く。
static Parser<char> JChar =
    new OrParser<char>(
        new ConditionalCharParser(it => it is not ('"' or '\\')),
        ControlChar);
```

通常文字の受理条件、成功時の値と1文字の前進、失敗時のカーソル、外側のOrとControlCharによるエスケープ処理を維持する。本体、公開API、依存関係、テストは変更していない。固定2文字の判定を既存部品へ任せ、解析処理を手書き展開していない。

ソース上、両版ともNULを通常文字として受理し、Currentが終端で返すNULも同じ扱いになる。既存の終端・不正入力の扱いを是正する変更ではなく、これを意図されたJSON仕様や包括的な規格適合性の保証とは扱わない。

## 根拠と生成コード

基準のExpectCharParser経路には、内側Orの候補配列走査、各CharParserの型ガード・Current取得と範囲判定・IgnoreCase分岐、除外対象でなかった場合のCurrent再取得が残っていた。通常文字では2候補とも不一致になる。単にメソッド呼び出しを減らすという仮説ではない。

別プロセスで採取した両版のTier 1コードを比較した。候補の通常文字predicate `JSON+<>c.<.cctor>b__37_9(char)` は、Dynamic PGO Tier 1で引用符34・バックスラッシュ92を比較する21 bytesのコードとなった。内側Orの候補走査と最後の文字再取得がなくなり、候補ではExpectCharParserのTier 1コードは採取されなかった。

ただし外側OrのConditionalCharParser展開には、空白predicate `b__37_0` 向けのdelegate guardが残り、通常文字predicateは不一致側のFunc.Invokeへ進む。完全なPGO非依存化ではない。Or<char>のnative code sizeは498から358 bytesへ変化したが、この比率を速度効果とは扱わない。通常計時の結果にはprofileや展開の変化も含まれ、削減した個々の処理の寄与率は分離していない。新たなCPUサンプリングは行わず、JIT診断付きの時間は速度比較に含めていない。

## 測定条件

入力は既存 `Data/test.json`、4,172,062 bytes、SHA-256 `DC87DD0FB85CB6F875AC336B70FEFC1E32BB1F284C8F6E011E0CB0256F9A354D`。MemoryStreamの作成・コピー、UTF-8からstringへの復号、全文解析と結果木生成を含み、物理ディスク読み取りは含めない。両版で全文消費、100,001ノード、System.Text.Jsonとの木の一致を確認した。System.Text.Jsonは結果検証用で、速度の比較対象ではない。

SDK 10.0.401、.NET 10.0.12、BenchmarkDotNet 0.15.8、Windows 25H2 build 26200.9711、i7-13700H。PGO有効、affinity mask 4、warmup 16、Actual 8、invocation 4、unroll 1、DontRemove。各系列は新規プロセス8組16起動、奇数組は基準→候補、偶数組は候補→基準。各起動の8 Result平均を単位として、8個の対応log時間比の95% t区間（自由度7、t=2.364624251）を求めた。ActualとResultを独立した標本として数えない。

探索で区間上限が1未満なら独立8組へ進み、確認でも上限が1未満の場合だけ性能面の採用条件を満たす。途中結果による組数変更・外れ値除外は行わず、探索と確認は合算しない。計測はLuna medium担当が直列実行し、親のビルド・テストを重ねていない。

基準の固定hostを複製してJSONサンプルのDLL/PDBだけを交換した。28 DLLのmanifestで異なるのはMarimo.Parser.dllだけ。本体DLLは両版とも `711A6D91E2BF0132ABB50DEC81A5B80555CDDF2BD0F4D3B8F5C849AC2F676BA8` を再使用した。本体ソースに変更はないが、親の新しいビルドでは本体DLLハッシュが変わったため、その新しいDLLを片側だけへ持ち込んでいない。ハッシュ差の原因は特定していない。

独立確認では約5.34%短縮、区間は約3.76〜6.89%短縮で、事前条件を満たした。解析中の割り当ては両版とも約49.845 MB/解析で同水準。割り当て削減ではなく判定の重複削減を狙った候補として評価する。この入力・環境での効果であり、別の文法や入力全般へ一般化しない。

全32起動が正常終了し、各Actual/Resultは8反復、各反復4操作だった。探索2組目の起動前external-loadログだけは、記録スクリプトのStage引数制約により取得に失敗した。AC・省電力・helperの別途確認は成功していたが、後取りの負荷ログで補った扱いにはしない。その組も除外せず、追加測定もしなかった。以後は記録失敗時にランを始めないようにした。

独立確認8組はすべて起動前ログを保存し、AC接続・省電力無効・helper稼働を確認した。保存済みの3秒窓では他のdotnetのCPU活動を検出しなかった。ただし、これは測定中の全プロセスの外部負荷が常時ゼロだったという保証ではない。
