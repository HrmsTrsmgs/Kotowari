# Refactor：外部契約を保って内部設計を改善する

G時点の現行コード・テスト・契約、対象設計領域の命名・品質規約、必要な呼び出し元と先を
読む。Greenの思考過程や未実装要求の一覧は引き継がない。差分は読む場所の索引であり、
現行コードの代用品にしない。継続担当は最後の同期SHAからGまでを確認する。

* 今回追加した行だけでなく、対象の設計領域にある重複、名前・構造、長すぎる処理、責務、依存関係、変更波及、既存方針との不整合を検討する。
* 似たコードは意味と変更理由が同じ場合だけ共通化する。形式的な抽象化、まだない将来機能への備え、不要な依存関係を追加しない。
* 内部設計と読みやすさに加え、実装の意味、アルゴリズムの正当性、ロジックの不足を検討する。Greenでテストが通ったことだけを理由に検討を省略しない。
* 外部振る舞いを保つ小さな変更を重ね、必要なテストと回帰検証を実行する。テスト成功を任意の書き換えの同値証明とは扱わず、自動テストも目視だけで代替しない。
* クラスやメソッドの抽出は既存振る舞いの移動に限定し、新しい入力、例外、保存機能などを混ぜない。テスト整理でも意図、評価回数、Skip状態を不用意に変えない。
* 不足機能や誤りはここで実装せず、重複を確認して次のRed候補として短く残す。外部契約変更が不可欠なら停止する。

改善すべき実問題がなければ変更せず、Fコミットも空コミットも作らない。実変更があれば
検証後も未コミットのまま人間の差分確認を待ち、対象ファイル、構造変更の要点、メッセージ案、
コマンドと結果を進行役へ返す。この担当でGreenを兼任しない。
