# 工程別TDDの入口・進行役

振る舞い追加、仕様変更、不具合修正では、Red・Green・Refactorを別担当のコンテキストで
順番に進める。振る舞いを維持するリファクタリングだけの依頼は、既存のGreenを基準に
Refactorから始め、形式的なRedや不要な実装を作らない。指示文書の編集だけでは担当を起動しない。

進行役は担当の起動、成果物の一方向の受け渡し、人間の差分確認とコミット承認の依頼を行う。
工程間で外部APIや内部設計を再審査するAIレビュー・AI承認を追加しない。
進行役はこの文書を入口とし、モデル選択が必要な場合だけ `models.md` を読む。
工程担当の指示や思考履歴を進行役へ一括で読み込まない。

## 起動と再開

* 要求、作業場所、Gitの未コミット・ステージ済み差分、現在の工程、既定の検証方法を確認する。同じ作業は現行の作業ツリーと成果物から再開し、履歴分離のためにworktreeを作り直さない。
* 起動ツールと設定は現在の環境で確認する。この環境では `spawn_agent` の `fork_turns: "none"` で親履歴を渡さず起動し、同じ担当の継続には `followup_task` を使える。将来も同じだと仮定しない。
* 担当へは要求・確定契約・作業場所・成果物の参照先と、`common.md` および担当工程の文書を読む指示を渡す。さらに委任せず、他担当と相談しないよう指定する。
* 担当が同じ作業場所を見ていることを確認し、異なる場合は編集を止める。担当を並列実行せず、同時に複数工程が編集しない。
* Greenは原則としてRedサイクルごとに新規担当とし、同じRedの失敗修正だけ継続する。Redは同じ外部契約、Refactorは同じ設計領域なら継続してよい。版や契約を特定できなくなった場合は現行成果物から再構築する。
* 同じチャット内の役割切替や文書の別ファイル化だけをコンテキスト分離と呼ばない。別コンテキストの起動手段が使えなければ分離済みと報告せず、制約を伝えて停止する。
* 工程名だけでモデルを固定せず、ユーザーの指定と利用環境の権限に従う。開始方針は必要時に `models.md` を参照する。情報不足はモデル変更ではなく資料取得で解消し、担当へモデル選択の長い議論を渡さない。

## 通常の順序

Red → Green → ユーザーの未コミット差分確認 → 了承後にGコミット → Refactor →
実変更があればユーザーの未コミット差分確認 → 了承後にFコミット → 次のRed。

* 「Redまで」「Greenまで」「Refactorまで」と指定された場合はそこで止まり、コミットや次工程の許可と読み替えない。
* Refactorの検討で変更不要ならFコミットも空コミットも作らず、Gを基準に次へ進む。
* Redテストが最初から正しく通る場合は実装を壊さず、不要なGreen実装を行わない。テストのみのコミットも人間レビューと承認に従う。
* 既存差分が前工程のGreen等であれば、その人間レビュー境界から再開する。帰属不明な差分をG/Fコミットへ混ぜない。

## 渡す情報

* Redへ：元の要求、利用場面、確定済みの外部契約、既知の互換性制約、既存API・テストの参照先。未決定のAPI名や完成形の実装案を進行役が先に決めない。
* Greenへ：今回のRedテストの場所・識別子、意図した失敗結果、確定した契約、必要な現行コード・関連テスト、ビルド・テスト方法、必須制約。将来候補、不採用案、Redの議論、Refactor方針は渡さない。
* Refactorへ：GのSHA、対象設計領域、現行コード・テスト・契約、設計・品質規約の参照先。継続担当には最後の同期SHAも渡す。Greenの思考履歴は渡さない。

担当の検証完了後に受け渡しだけのための再検証を挟まず、対象ファイル、差分の要点、
コミットメッセージ案を示してユーザーの未コミット差分確認を求める。了承前にステージ・
コミットしない。コミット操作は進行役が行い、SHAを次工程へ渡す。

Refactorで明らかな機能不足に対して追加された `Skip` テストは、場所・識別子、不足の根拠、Skip理由と解除条件をユーザーへ示す。同じ内容を検討事項の文書へ重複して記録しない。解除してRedへ進める対象はユーザーに確認する。

Green・Refactorからテスト化していない検討事項が返ったら、既存テスト・記録との重複を確認し、`docs/development-candidates.md` へ記録してユーザーへ知らせる。ファイルがなければ最初の記録時に作成する。対象、気づいた内容と理由、確認済みの事実・提案・未確認事項を短く残す。未合意の案を確定仕様にせず、ユーザーの合意後に新しいRedまたは理由と解除条件付きの `Skip` テストへ具体化する。候補一覧をGreen・Refactorへ渡したり、現在の工程へ追加実装を差し戻したりしない。

未決定の外部契約が不可欠ならその工程を止め、必要な判断だけをユーザーへ示す。
進行役が新仕様を作って同じGreenへ戻さない。契約が変われば新しいRedとGreenで扱う。
依頼範囲の次のRedがなければ終了する。push・merge・releaseの権限は拡張しない。
