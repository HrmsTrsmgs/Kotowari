# Green：今回のRedを直接通す

今回のRedテスト、確認済みの失敗、確定した外部契約、必要な現行コード・関連テスト、
ビルド・テスト方法、必須制約を参照する。将来候補、不採用案、Redの設計議論、
内部設計改善資料、過去の工程履歴は原則として受け取らない。

* 失敗の直接原因を確認し、最初に見つかった直接的な実装を試す。現在と既存の契約を満たすなら定数返し、特殊ケース、一時的な重複、不格好なコードを許容する。明らかな既存処理があるのに、わざとハードコードしない。
* 未要求の入力、例外、並行性、破棄保証、再試行、復旧、将来拡張、共通化、責務整理、抽象化を先取りしない。最小コードの証明や別アルゴリズムの網羅比較は行わない。
* Redの期待値や契約を実装へ合わせて弱めない。テストの削除・Skip化・実行除外でGreenにしない。未決定の外部契約が不可欠なら停止する。
* 小さく実装して対象テストを実行し、結果に従って修正する。長く成功を推論するより自動テストで確認し、既存の関連・全体回帰も検証する。
* 仕様変更で他のテストが失敗した場合は、新契約へ合わせるべき期待と維持すべき既存契約の回帰を区別する。前者は新しいRedの対象として扱い、後者は実装を修正する。全体のGreen前にRefactorへ進まない。
* 既存のSkip対象へ波及する共通処理や対象外のテスト・データ整理が必要なら着手前に報告する。対象外テストを失敗させ続けるために実装を歪めない。
* 成功後は今回のGreen差分を一度確認し、使われないコード、試行の残骸、未要求の分岐・例外・将来対応、ログ、二重実装を除く。除去後は影響する検証を再実行する。より短い方式の探索、共通化、正当性の精査はRefactorへ残す。

必要な検証後もコミットせず、ユーザーがIDE等で未コミット差分を確認できる状態にする。
対象ファイル、差分の要点、メッセージ案、コマンドと結果を進行役へ返し、このGreenを終了する。
今回のRedとGreenをGコミットへ含めるかどうかは人間レビューと承認に従う。
