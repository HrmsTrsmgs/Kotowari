# Red：利用側から外部契約を設計する

今回の未充足の振る舞いを一つ、またはユーザーと合意した小さな仕様群として選ぶ。
責務、呼び出し方、入力、戻り値、外から見える状態変化を利用者側から考え、実装の
容易さや完成形の内部構造からAPIを逆算しない。確定済み契約は設計し直さない。

* 対象機能、同じ公開境界、類似ユースケース、代表的な呼び出し側、互換性に関係する既存テスト・APIを検索し、必要なものだけ読む。既存テストの意味を根拠なく現行契約・旧仕様と決めつけない。
* 既存コードの確認はAPI宣言と利用例を中心に行い、対象の内部アルゴリズムやGreen・Refactorの履歴は原則として参照しない。全件テスト計画や完成形の実装案を先に確定しない。
* テストに実際の利用側の呼び出しを書き、名前、引数の意味・順序、booleanや文字列の意味、不要な状態管理、既存の類似APIとの整合を読み直す。「可読性を考慮した」という宣言より実際のコードを判断対象にする。
* 期待値は要求と確定契約から決め、現行実装の結果を写さない。複数Assertで同じ振る舞いを説明してよいが、独立した仕様を一つへ詰めない。
* 仕様変更が合意済みなら対象の既存テストを新契約へ変更し、維持する他の契約を弱めない。新しく明示する例外契約は原則として先にテストで固定する。
* テストを実行し、意図した未実現の振る舞いで失敗したことを確認する。API未存在、最小スタブ、対象の振る舞い、環境障害による失敗を区別する。APIが必要なら宣言や `NotImplementedException` スタブだけを追加してよい。
* 意図と違う失敗ならテスト・データ・契約を見直し、Greenを始めない。最初から正しく通る場合は実装を壊さない。
* 合意済みの後日の観点を記録する場合だけ、重複を確認して理由と解除条件付きの `Skip` を使う。解除対象はユーザーへ確認し、未合意の将来仕様を先取りしない。

テスト、必要なAPI宣言、確定契約、実行結果を成果物として返す。今回の場所・識別子・
失敗結果・契約だけを短く報告し、Green実装へ進まず終了する。
