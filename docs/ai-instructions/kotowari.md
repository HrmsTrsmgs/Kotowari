# Kotowari固有作業指示

## プロジェクトの目的

Kotowariを、第三者がビルド、テスト、利用、レビューできる、依存関係のないC#用パーサーコンビネーターライブラリとして整備する。

* 公開APIの理解しやすさ、組み合わせやすさ、診断可能性、テスト可能性を優先する。
* 利用側コードの簡潔さ、変更箇所の局所化、責務分離を重視し、内部実装の都合を利用者の手順へ押し付けない。
* ライブラリ本体を特定の構文やデータ形式へ結合しない。
* 必要性が確認できない抽象化、汎用化、依存関係を追加しない。

## 公開APIと互換性

* 公開APIの変更前に、既存利用コード、テスト、サンプル、対象フレームワークへの影響を確認する。
* 公開API案は可能な限りRed段階の実際の呼び出しコードとして示し、名前、引数、戻り値、利用感をレビューできる形にする。
* 対象フレームワークは `net10.0` とする。対象フレームワークを追加・変更する場合は、利用側と配布への影響を明示してユーザーの了承を得る。
* パッケージの依存関係を増やす変更は、dependency-freeという製品特性への影響を確認する。テストやベンチマークだけの依存とは区別する。

## JSONサンプルとベンチマーク

* 小さな振る舞いのテストには最小の入力を使い、性能比較用の大きなJSONサンプルとは役割を分ける。既存の測定入力を無断で縮小・再生成・置換しない。

* JSONパーサーはKotowariの使用例および性能比較用であり、ライブラリ本体の目的と混同しない。
* 参照元のSpracheJSONは最新版を基準とし、比較対象に対するテストをKotowari側へも適用して実装を合わせる。参照したコミットと比較用パッケージの版は区別する。値モデルや周辺機能を独立したJSONライブラリとして独自に修正・拡張しない。
* 不足している確認は比較対象とKotowari側の両方へ追加してよい。比較対象の機能不足はその実装の仕様として扱い、JSON規格等から独自の期待を持ち込んで片側だけ修正しない。共通テストは同じ入力・観測で移植差を検出する。
* 参照元との同期で、以前合意した文法や測定の仕事量が変わる場合は差を示し、変更範囲を確認する。最新版への追従を理由に既存の合意やテストを無断で取り消さない。
* 参照元からの取り込みの経緯、仕様の基準、テストと測定で確認する内容・未確認事項は[開発の判断記録](../development-context.md#json比較実装の参照元と検証の目的)を参照する。
* ベンチマークでは、入力ファイル、サイズ、ハッシュ、環境、ランタイム、依存バージョン、ジョブ設定を記録する。
* 比較対象が入力全体を消費し、結果を生成したことを測定前に検証する。部分解析や失敗したアダプターの時間を比較結果に含めない。
* 専用パーサーとパーサーコンビネーターを同列の主比較として扱わず、専用パーサーは参考値と明記する。
* 生成結果や処理量が異なる場合は差を記録し、厳密に同一の仕事量であると断定しない。
* 旧比較対象を残す場合は、互換性警告、手動参照、検証緩和など現行環境で必要な条件を隠さない。
* 単発値で一般的な優劣を断定せず、同一環境・同一入力・同一測定条件で観測した結果として報告する。

## 性能改善と記述方針

* LINQの記述方針だけを理由に、パーサーの走査ループやSpan処理を無理に列挙へ変換しない。性能上の選択は測定結果または確認できる割り当て・評価回数の根拠を示す。
* 最適化でも入力消費、成功・失敗、値、診断、互換性の契約を維持する。構文整理とアルゴリズム・割り当ての変更を混ぜない。

## 文書と公開準備

* READMEのビルド、テスト、ベンチマーク手順を実在する構成と一致させる。
* 未実装機能や未確認の互換性を利用可能なものとして記載しない。
* READMEは初めて使う人が目的、最小利用例、制約を理解できる順にする。公開準備と実際の公開を区別し、公開やreleaseを準備依頼だけで実行しない。
* ライブラリ本体、テスト用JSONパーサー、ベンチマーク用アダプターの責務を文書上でも区別する。

## AI用スクリプトとSkip管理

* AI向けの作業補助は `scripts/ai/` に置く。Skip解除には `scripts/ai/Enable-NextSkippedTest.ps1` を使う。PowerShell 7.6以降が必要で、同梱のRoslynでC#構文を解析する。パッケージの追加は不要。
* 新しいSkip理由は既存のテストに合わせて `[グループ名 001] 理由と解除条件` の形にする。グループ名がない場合は `[001] 理由と解除条件` とする。番号は同じグループ内で一意の正の整数とし、解除後の振り直しは不要。`グループ名 001: 理由` と `001: 理由` も同じメタデータとして読める。
* 解除するグループをユーザーと決めた後は、AIがスクリプトを実行してよい。`-Group` はグループ名の完全一致で選ぶ。省略した場合はグループ名のないSkipだけを選び、別グループへ自動で進まない。
* 選択範囲では最小番号の一件を解除する。グループ名も番号もない従来のSkipも扱い、無グループの番号付きSkipの後で、ファイル名・ファイル内の出現順に一件ずつ選ぶ。既存Skipの一括改名や一括解除を前提としない。
* データごとに段階的に扱う場合は、xUnit v3の `InlineData` の `Skip`、または `TheoryDataRow` の `Skip` プロパティ・`WithSkip` に記す。全体が未対応の場合だけ `Fact`・`Theory` 全体のSkipを使う。データ単位のSkipと、そのデータを妨げるTheory全体のSkipを重ねない。
* スクリプトは通常の `Fact`・`Theory`・`InlineData`・`MemberData`・`ClassData` 属性と、型をソースから確認できる `TheoryDataRow` の初期化・`WithSkip` を対象にする。理由は文字列リテラルで記載する。定数参照などの式は実行・評価せず停止する。対象なし、番号重複、構文エラーの場合も書き込まない。
* 標準の探索先は `Kotowari.Tests`、`JsonParserのテスト`、`SpracheJson.Reference.Tests`。`-Path` でC#ファイルまたはディレクトリを限定できる。相対パスはリポジトリ基準。`bin`・`obj` 等の生成物とリンク先を探索しない。
* `-WhatIf` で書き込まずに対象を確認できる。実行結果のファイル・行・理由とGit差分を確認し、解除した対象テストを実行する。意図したRedか、既に通る確認かを区別し、後者を失敗させるために本体を壊さない。解除だけを理由に次のSkipや本体実装へ進まない。

```powershell
# グループ指定ありの事前確認と解除
pwsh -NoProfile -File scripts/ai/Enable-NextSkippedTest.ps1 -Group 空白処理 -WhatIf
pwsh -NoProfile -File scripts/ai/Enable-NextSkippedTest.ps1 -Group 空白処理

# グループ名なしの事前確認と解除
pwsh -NoProfile -File scripts/ai/Enable-NextSkippedTest.ps1 -WhatIf
pwsh -NoProfile -File scripts/ai/Enable-NextSkippedTest.ps1

# スクリプトの回帰検証（一時フィクスチャだけを変更する）
pwsh -NoProfile -File scripts/ai/tests/Test-Enable-NextSkippedTest.ps1
```

## 実行中のスリープ抑止

* 依頼された作業の実行中は、実行マシンの自動スリープを一時的に抑止する。測定だけでなく、準備、調査、ビルド、テスト、解析、結果整理、ツール・サブエージェントの完了待ちも対象とする。
* 親が作業全体の抑止期間を管理する。個々のコマンドや計測担当が終了しても、後続作業がある間は解除せず、コマンド間にも抑止の空白を作らない。
* OSが提供する一時的な抑止機能を使い、呼び出したプロセスやスレッドの終了後も必要な期間を保護できる管理方法を確認する。短命なコマンドから一度呼ぶだけで継続すると見なさず、既存の仕組みの有無と有効期間を確認する。
* 作業完了、取り消し、中断、ユーザーの回答待ちで作業を停止するときは解除する。異常終了時にも抑止だけが無期限に残らないようにし、期限付きの仕組みでは作業中に期限が切れないよう管理する。
* 抑止の取得・維持・解除を確認し、作業ログに記録する。取得や維持ができなければ報告し、保護されている前提で進めない。
* 電源プラン、自動スリープ時間、蓋や電源ボタンの設定を恒久変更しない。画面の点灯維持は別の要求として扱い、ユーザーによる明示的なスリープやシャットダウンを妨げない。

## 性能計測の担当

* 性能計測の準備、定型実行、機械的な検証、集計は、Luna・推論レベル `medium` のサブエージェントへ任せる。この環境では `gpt-6-luna` が起動可能と確認できる場合だけ指定する。委任機能を使える統括から起動し、利用できない場合は勝手に別モデルへ切り替えず報告する。
* 親は改善仮説、測定条件の決定、結果の解釈、変更の採用判断を担当する。計測担当をリファクタリング担当と混同せず、ライブラリ本体の変更は任せない。
* 計測担当には対象実装の版、入力、確定した条件、既存スクリプト、記録先を渡す。通常は要約と成果物を受け取り、親が生ログを重複して読むのは異常や不明点の確認に必要な場合に限る。
* 同じマシンでの測定は直列実行し、計測中に親や他担当が重いビルド・開発処理を並行して走らせない。
