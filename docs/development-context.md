# 開発の判断と再開地点

仕様や設計の経緯を思い出し、同じ議論を繰り返さずに開発を再開するための入口。
詳細は既存のテスト・コメント・測定記録に置き、ここには参照先と、まだ置き場所のない重要な判断だけを残す。
主担当・進行役が現在状況と関連資料を確認し、工程担当には既存のTDD手順に沿って必要な情報だけを渡す。

### JSON比較実装の参照元と検証の目的

**採用方針／2026-11-05にユーザー確認。** この節を、JSON比較実装の経緯と判断理由の記録先とする。作業時の短い規則は[固有指示](ai-instructions/kotowari.md#jsonサンプルとベンチマーク)、個々の振る舞いはテスト、測定条件と結果は[測定記録](../Kotowari.Benchmarks/Results/README.md)に置く。

#### 目的と、何を正とするか

`JsonParser` は、比較対象のSpracheJSONによるJSON解析をKotowariのパーサーコンビネーターで実装し、性能を比較するための使用例である。独立したJSONライブラリを完成・保守することは目的ではない。解析結果の値モデルも比較の仕事量に関わるため、単に同じ入力を受理すれば比較が成立するわけではない。

| 確認対象 | 正しさの基準 | 確認する内容 |
|---|---|---|
| JSON移植の振る舞い | 参照する版を特定したSpracheJSONの仕様・振る舞い | 同じ入力に対する解析の成功・失敗、生成結果の構造・型の対応・値などに移植差がないか |
| Kotowari本体 | 開発者と合意した本体の契約・既存テスト | 各コンビネーター、カーソル、結果型の契約を満たすか。SpracheJSONの振る舞いを本体全体の仕様にはしない |
| 性能比較 | 同じ入力・条件で、比較可能な処理を完了した実装 | 入力全体の消費、結果の生成と処理量を計時外で確かめたうえで、時間・割り当て等を測る |

JSON移植では参照元の最新版を基準とし、実際に追従・検証するコミットを固定する。SpracheJSONの機能不足はその実装の仕様として扱い、JSON規格やAIの考える理想のAPIを根拠にKotowari側だけ機能を補わない。これは参照元がJSON規格に完全準拠しているという意味ではなく、比較の基準をそろえるという意味である。

#### テストの役割

基本の流れは、比較対象に対して振る舞いを確認するテストを用意し、そのテストをKotowari側にも適用して実装を作ることである。不足するテストは両方に追加してよい。

* 同じ入力と同じ観測内容を両実装へ適用し、比較対象で確認した仕様を期待値にする。型名や呼び出し方の違いは対応づけるが、片側だけ期待値を弱めない。
* 未対応を確認するケースも仕様確認になる。「両方に、同じ未対応機能の実装を要求するテストを追加する」という意味ではない。
* 差が見つかったら、まず参照した版の違いか、移植による違いかを分ける。参照元由来の振る舞いを発見しただけで、Kotowari側だけの不具合修正へ進まない。
* 既存のJSON規格対応など、以前合意した参照元との差は明示して扱う。同期を理由に既存テストを黙って削除・反転しない。

このテストはJSON移植の同等性を確認するものであり、それだけでJSON規格全体への準拠や、全比較ライブラリの仕事量の一致、性能の優劣を証明するものではない。

#### 取り込みの経緯と参照する版

以下はGit履歴と2026-11-05の参照元調査で確認した事実である。

* `69bf755`（2019-10-17「組み立てるJsonrリテラルの導入」）で、Ian Woldの著作権表示とMITライセンス付きの値モデルが入った。この時点ですでに `JSONLiteral.Get()` と、それを使う `JSONMap.MapLiteral()` がある。Getは今回AIが新設したAPIではない。
* 2020年の履歴には `SpracheJSONのテスト/JSONのテスト.cs` と `JsonParserのテスト/JSONのテスト.cs` がある。たとえば `bc22c12`（2020-08-16）では前者の `JSON.Parse("{}")` に対するテストに対応して、後者で当時の `JSON.ParseAsync("{}")` をテストしている。参照元をテストし、Kotowari側にも展開していた流れを確認できる。
* 当初の取り込みがfork経由だったか、どの版をどの手順で取り込んだかまでは確認できていない。「単純コピーだった」「forkではなかった」とは断定しない。

名前が似ている次の3つは区別する。

| 対象 | 確認した版と役割 |
|---|---|
| [IanWold/SpracheJson](https://github.com/IanWold/SpracheJson) のソース | 調査時のmasterは `aa8092aa4f5a7f1675200ac908d20c06e285aec4`（2022-11-08）。最新版への追従の基準。まだこちらへ同期していない |
| NuGetのSpracheJSON | 現在の比較用パッケージは `1.0.1`。ベンチマークの `SpracheJsonPackage` が呼ぶ旧実装で、上記ソース版と同一視しない |
| パーサーコンビネーターSprache | 現在の依存は `2.3.1`。ベンチマークの別行 `Sprache` は [SpracheJsonParser](../Kotowari.Benchmarks/SpracheJsonParser.cs) を使い、旧SpracheJSONパッケージの行とは別物 |

パッケージ版の正本は [Directory.Packages.props](../Directory.Packages.props)。参照元ソースの再帰的ファイル一覧にはテストプロジェクトがなく、今回「上流に備え付けのテストをコピー済み」とは確認していない。履歴にあるSpracheJSON向けテストと、上流自身のテストを混同しない。

#### Getの独自修正を取り下げた理由

全体レビューのR04では、こちらの `JsonLiteral.Get()` が文字列 `"1.2"` を数値へ変換すると、実行カルチャーによって1.2・12・例外になる現象を確認した。AIは用途と参照元の確認をせず、カルチャー非依存にする期待を追加して、固定カルチャーを使う実装へ変更した。

しかし、参照元の[上記コミットのGet](https://github.com/IanWold/SpracheJson/blob/aa8092aa4f5a7f1675200ac908d20c06e285aec4/SpracheJson/SyntaxTree/JsonLiteral.cs)も、ソース上は `Convert.ToDouble(Value)` を使っている。これは移植で新たに生じた違いを直す修正ではなく、参照元にはない仕様を片側だけに追加するものだった。ユーザー確認後、実装とその独自仕様を要求するテストを未コミットのまま取り下げた。

さらに、現在の[計時対象](../Kotowari.Benchmarks/JsonParserBenchmarks.cs)はParseによる解析結果の生成であり、Getやオブジェクトへのマッピングは呼んでいない。Getは[JsonMap](../JsonParser/JsonMap.cs)が使う値変換の補助機能である。「数値の字句を解析してValueに保持する処理」と「Getでdoubleへ変換する処理」は別であり、今回の変更は速度比較の処理を改善するものでもなかった。

採用しなかったのは「JSONとして一般に正しそうだから、片側のGetだけを直す」進め方である。不足する確認を両側に追加することや、将来の参照元変更へ追従することまで否定したものではない。R04の観測事実は[候補一覧](development-candidates.md#r04json数値の取得結果が実行カルチャーで変わる)に残す。

#### 現在確認できていること・まだ確認していないこと

* Getのカルチャー差はKotowari側で実行確認した。最新参照元が同じ変換を使うことはソースで確認したが、その版を起動して両実装へ同じテストを通したわけではない。
* 現在の[JSONテスト](../JsonParserのテスト/Jsonのテスト.cs)はKotowari側のテストであり、最新版SpracheJSONと共通実行する仕組みはまだ整備していない。今回、新しい共通テストを追加したとは扱わない。
* 現在の `--validate` は各解析処理を呼び、生成木のノード数を表示する。全消費や値の一致を検証するアサーションはなく、ノード数の表示だけで公平な比較を保証しない。過去の測定で追加確認した範囲は、それぞれの[測定報告](../Kotowari.Benchmarks/Results/README.md)を参照する。
* 最新参照元との文法・値モデル・APIの差は調査段階で、同期は未実施。数値各部に0桁を許す上流文法と、こちらの `3ce37e5` のJSON規格対応など、既存差も残っている。今後は対象版と比較範囲を示し、両実装に同じテストを適用して差を確認する。
