# 開発の判断と再開地点

仕様や設計の経緯を思い出し、同じ議論を繰り返さずに開発を再開するための入口。
詳細は既存のテスト・コメント・測定記録に置き、ここには参照先と、まだ置き場所のない重要な判断だけを残す。
主担当・進行役が現在状況と関連資料を確認し、工程担当には既存のTDD手順に沿って必要な情報だけを渡す。

## 運用と記録の置き場所

仕様を必要時に質問し、重要な合意を記録し、中断時に次の着手点を残す。
更新の基準と事実・推測の区別は、[共通指示の「仕様の確認と継続記録」](ai-instructions/common.md#仕様の確認と継続記録)に従う。

| 残す内容 | 置き場所 |
|---|---|
| 開発・設計の規則、確定した制約 | 既存の[共通指示](ai-instructions/common.md)、[C#指示](ai-instructions/csharp.md)、[Kotowari固有指示](ai-instructions/kotowari.md) |
| 振る舞いの具体例・境界条件 | 既存テスト。説明が必要な意図や理由だけを補い、ケース一覧を複製しない |
| 設計判断・理由・不採用案 | 既存の責務コメント・設計資料・測定報告を優先。置き場所がなければ下の「判断記録」に短い項目を追加 |
| 未確定仕様・検討事項 | [既存TDD手順](ai-instructions/tdd-context/run.md)に従う。テスト化していない事項は必要時に[開発候補一覧](development-candidates.md)へ記録する |
| 作業の停止位置・次の着手点 | この文書の「現在の作業状況」を置き換える。過去はGit履歴を参照 |

### 軽量AI-DLCの適用範囲

2026-10-19のユーザー依頼に基づき、必要な仕様の引き出し、判断の蓄積、再開時の文脈復元を補う。
[AWSのAI-DLC解説](https://aws.amazon.com/blogs/devops/open-sourcing-adaptive-workflows-for-ai-driven-development-life-cycle-ai-dlc/)の、作業に応じた深さと人間による判断を重視する考え方を参照した、個人OSS向けの運用である。
全工程の形式的な導入、専用ツールの追加、大規模な仕様書、判断ごとのADRファイル、追加の承認工程は導入しない。記録負担を抑え、既存のTDDと記録をそのまま使うためである。
Codexからの入口には既存の [AGENTS.md](../AGENTS.md) を使う（[公式のAGENTS.md説明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)）。

## 仕様と制約の参照先

2026-10-19に現行資料とコードを確認した。以下は網羅的な仕様書ではない。

* **既存文書で明文化済みの方針**：dependency-freeのC#パーサーコンビネーター、公開APIの組み合わせやすさ・責務分離、対象 `net10.0`、JSONパーサーは使用例兼性能比較用。詳細と変更時の制約は [Kotowari固有指示](ai-instructions/kotowari.md)、構成と実行方法は [README](../README.md) を参照する。
* **テストで表現された現状**：[ParseResultのテスト](../Kotowari.Tests/ParseResultのテスト.cs)が成功・失敗・値取得・null拒否を、[各コンビネーターのテスト](../Kotowari.Tests/Core)が組み合わせと境界条件を表す。[JSONのテスト](../JsonParserのテスト/JSONのテスト.cs)はサンプルの振る舞いを表す。JSON nullの値表現と、ParseResultの成功値へのnull指定は別である。
* テストは重要な仕様資産だが、既存コードとテストのすべてを開発者が意図した仕様、またはJSON規格への適合保証とは扱わない。仕様変更に必要な疑問は、その箇所の既存記録を確認してからユーザーへ尋ねる。

## 判断記録

初期記録は既存資料に明記された判断に限定した。既に理由が残る項目は索引として置き、ここで再決定しない。

### 内部ParseCore呼び出しは実測対象に限る特例

**採用済み方針／2026-10-05の記録を2026-10-19に確認。** 通常は子パーサーにも `Parse` を使う。内部の直接 `ParseCore` 呼び出しは、実測したPGO対策対象の特例であり、単なる呼び出し削除や手動インライン化の方針ではない。
理由と適用範囲は [ParserOfT.csのremarks](../Kotowari/ParserOfT.cs)、生成コード・採用根拠・検証の限界は [PGO呼び出し位置の比較](../Kotowari.Benchmarks/Results/2026-10-05-pgo-callsite.md)にある。採用コミットは `09dee2b`。
型profile混在による説明は最有力の**原因仮説**であり、生profile分布を確認済みとはしない。PGOを無効化して遅い側へそろえる案は解決策にしない。通常の `Parse` へまとめ直す場合の再検証条件もremarksに残っている。

### UTF-8試作は終了し文字列専用へ戻した

**撤回済み／2026-10-12の判断、2026-10-19に履歴確認。** `ce377dc` でUTF-8試作を撤回し、文字列専用実装へ戻した。
速度目標の未達と個別案の採用見送りは [最終測定記録](../Kotowari.Benchmarks/Results/2026-10-12-utf8-character-advance.md)、残した実装・撤回範囲・保存タグは [UTF-8実験履歴](utf8-experiment-archive.md)にある。
旧比較基準Oは実際のUTF-8導入前ではなかったため、過去の比率を真の導入前との比較へ読み替えない。効果のあった複合案も記録に残っており、「すべて無効だった」「UTF-8対応は不可能」とは結論しない。将来再検討するときは、この訂正と保存版から確認する。

### その他の性能改善の採否

[測定記録の索引](../Kotowari.Benchmarks/Results/README.md)から、個々の実装版、条件、効果、採用・不採用理由をたどる。再適用やロールバックの判断も各報告とGit履歴を参照し、ここへ数値を転記しない。作業ツリー中の報告とコミット済みの判断は区別する。
